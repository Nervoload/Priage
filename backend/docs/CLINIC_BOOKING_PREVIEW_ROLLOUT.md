# Gated clinic booking preview rollout

This release extends the [clinic intake preview](CLINIC_INTAKE_PREVIEW_ROLLOUT.md) inside the existing NestJS monolith and PostgreSQL database. It is for local mock data and an internally restricted Azure staging rehearsal. It is not a public clinic launch: the deterministic interview, unapproved local test legal text, provider delivery approval, and remaining clinical/deployment controls are explicit gates.

## Deploy and configure

1. Retain a dedicated API deployment pinned with `PILOT_CLINIC_ID=<id>`, a `CLINIC_APPOINTMENT` tenant, and `CLINIC_PREVIEW_ENABLED=true` only behind internal network or identity access restrictions. Keep public deployments gated. Build both web apps with `VITE_CLINIC_PILOT_MODE=true` and the matching API/staff clinic settings from the intake rollout.
2. Apply additive migrations through `20260927100000_clinic_appointments` with `npx prisma migrate deploy`; regenerate the Prisma client for the deployed image. Perform the prior staff-profile backfill and resolve its manual-review report before using real data.
3. In Reception, an administrator sets the clinic IANA timezone, 15/30/60-minute slot length, per-slot capacity, pending-request hold (15–10080 minutes), and weekly hours. No hours are seeded. Add specific date closures and time blocks as needed. Review the clinic's actual schedule and cancellation policy before any real booking.
4. Publish **clinic and legal approved** Terms and Privacy Markdown documents from operator-owned files. Dry-run with `npm run clinic:publish-legal-document -- --kind TERMS --version <version> --file <approved.md>` and repeat for `PRIVACY`; inspect hashes and version labels. Add `--apply` to each command only after review. Existing versions are immutable. Do not publish the local `local-mock-booking-v1` smoke-test text outside the disposable local mock database.
5. Run an API and BullMQ worker process with access to the existing Redis. The `appointments` queue registers the every-minute expiry sweep. Read paths also expire stale requests, and capacity calculations exclude expired holds even if a worker is delayed. Monitor worker failures and queue backlog.

## Workflow and boundaries

- A guest or account patient starts a pinned-clinic visit with an unverified contact email. Completing the preview interview reveals server-calculated availability in clinic local time. A mandatory slot, current published Terms and Privacy document IDs, and affirmative acceptance are validated in one PostgreSQL transaction. The visit changes from `INTAKE` to `REQUESTED`; a pending slot consumes capacity only until the configured hold expires.
- Reception's **New appointments** shows only submitted slot requests. The current `STAFF` role represents Reception; administrators and clinical administrators can supervise appointment actions. Nurses and doctors can read the preview queue but cannot confirm or change appointments. IT administrators can manage schedule settings without access to the patient queue. Confirming a live request changes the appointment to `CONFIRMED` and encounter to `EXPECTED` in one transaction. Marking arrival is a separate action; it changes the encounter to `ADMITTED`. Decline, cancel, reschedule, no-show and expiry have explicit outcomes. Rescheduling a confirmed visit makes the new time provisional and requires Reception to confirm it again.
- Schedule changes and slot requests are serialized per clinic with a PostgreSQL advisory transaction lock. Appointments are tenant scoped; patients can access only their encounter, and Reception uses staff tenant membership. Request and action keys support safe retries. Refresh availability after a conflict.
- Visit acceptance records the exact Terms/Privacy versions and server timestamp. Links are shown at request submission and in the patient account. Approved content is not bundled in the software. An initial request does **not** trigger scheduling email. Reception confirmation now creates the confirmation/reminder outbox; see the [communications rollout](CLINIC_COMMUNICATIONS_PREVIEW_ROLLOUT.md).
- The Reception copy button exports basic name, visit contact, time and requested/confirmed status. The final PS-SUITE field order and wording need clinic sign-off. The patient must be matched to the correct chart before paste.

## Local rehearsal

Start a separate local clinic instance with `./priage-dev -t clinic` from the repository root. Enter its name, address, phone, timezone, check-in instructions and walk-in choice when prompted. The launcher creates a unique clinic hospital in its own PostgreSQL container/database and Redis container, pins the clinic API, and serves the clinic staff and patient apps on the printed ports (typically 5175 and 5176 for the first additional instance). It seeds mock weekday hours and mock Terms/Privacy documents only in that local database. `./priage-dev --instance NAME fullseed` creates mock intake, appointment and permitted walk-in visits. `./priage-dev --instance NAME -k` stops only that instance; the ED stack remains available. `./priage-dev -all -k` stops all registered instances while retaining their database volumes. These local defaults are not approved clinic schedule or legal copy.

Run the existing intake smoke test and `npm run test:clinic-booking-smoke` against the local pinned mock clinic API. The booking script creates mock schedule/legal records if needed and tests simultaneous requests for the last slot, duplicate keys, stale/legal rejection, queue membership, confirmation, arrival, reschedule/decline, account cancellation and expiry/capacity release. It changes local mock data and must never point at a real clinic database. Run `npm run check` in the backend and both web apps, plus the ED lifecycle regression in an unpinned API. Repeat guest/account and Reception browser journeys in restricted Azure staging with mock data.

## Remaining launch work

The [communications slice](CLINIC_COMMUNICATIONS_PREVIEW_ROLLOUT.md) now implements those flows with captured local email and optional restricted Resend delivery. The clinic questionnaire, approved Canadian model-backed assessment, clinic-approved Care export format, Azure service residency and production controls, and clinic UAT also remain. Do not present the preview as a completed clinical assessment or a live appointment notification service.
